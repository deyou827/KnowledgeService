# KnowledgeService 现行方案与开发入口

## 结论

项目相关文档放在项目仓库中。`docs/` 是本项目 PRD、技术方案、设计依据和实施计划的唯一维护位置，随代码一起版本管理，不依赖个人知识库或本机绝对路径。

## 阅读顺序

| 顺序 | 文档 | 读取目的 |
| --- | --- | --- |
| 1 | [产品需求文档](KnowledgeService-产品需求文档.md) | 企业角色、业务场景、权限语义、FR 需求和交付边界 |
| 2 | [技术方案](KnowledgeService-技术方案.md) | 领域模型、Capability／Provider、调用链、一致性、安全和运行保障 |
| 3 | [开源借鉴与设计决策](KnowledgeService-开源借鉴与设计决策.md) | 参考项目的采用理由、交互转化与待验证内容 |
| 4 | [实施与验收计划](KnowledgeService-实施与验收计划.md) | 本阶段产物、需求映射、验收门禁和暂不做的内容 |

## 开始一个阶段前

1. 阅读 PRD 与技术方案相关章节，明确企业目标和本阶段切片的区别。
2. 从实施计划确认阶段及 FR 编号、默认 Provider、权限边界、正常／异常验收条件。
3. 向用户说明为什么做、核心概念、与平台如何连接、取舍与不做事项，再按确认范围编码。
4. 文档缺失或相互冲突时先说明问题，不凭旧摘要猜测实现。

方案描述目标，不证明功能已经实现。实际状态以仓库代码、测试和运行验证为准；方案变更与对应实现一并评审，不能以文档更新冒充功能完成。

## 维护规则

- 项目 PRD、架构决策、接口说明、部署文档、实施计划和项目复盘保留在所属仓库。
- 使用仓库相对链接；方案改名或移动时更新入口及引用。
- 现行方案直接更新，不并行维护不同版本正文；历史由 Git 追踪。
- PRD 统一需求编号和交付边界，技术方案定义实现边界，实施计划引用需求编号，不另建产品范围。
- Obsidian 可保留项目导航和跨项目通用学习，不存放重复项目方案。
- 不提交个人知识内容、凭据、运行数据库或完整知识库。
