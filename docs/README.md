开工前 Review 收口见[详细设计 10.1](KnowledgeService-核心链路详细设计.md#101-开工前-review-收口)：配置派生产物、检索中撤权、草稿／发布隔离、幂等与版本检查顺序已明确。可进入 S1a 实现；数据库并发和真实模型验收仍待对应阶段完成。

2026-10-19 设计收敛以知识服务独立产品为主：ADR-0003 固定三类身份入口与默认 Keycloak claims、执行／回答／交付状态、取消请求标记、外部结果未知恢复规则和最小接口规格；技术失败不创建失败答案，同键保证不重复接纳操作而非外部模型恰好调用一次。技术方案第 15 节只定义目标调用方责任，不迁就旧平台问答。固定开源依据见[开源借鉴第 3.1 节](KnowledgeService-开源借鉴与设计决策.md#31-独立服务契约的固定源码依据)，实施顺序见[实施计划第 2.1 节](KnowledgeService-实施与验收计划.md#21-本轮契约优化的落地顺序)。本轮未改变默认存储或增加基础设施；正式 OpenAPI 与实现仍由对应阶段交付。

## 开始一个阶段前

1. 阅读 PRD 与技术方案相关章节，明确企业目标和本阶段切片的区别。
2. 从实施计划确认阶段及 FR 编号、默认 Provider、权限边界、正常／异常验收条件。
3. 向用户说明为什么做、核心概念、与平台如何连接、取舍与不做事项，再按确认范围编码。
4. 文档缺失或相互冲突时先说明问题，不凭旧摘要猜测实现。

方案描述目标，不证明功能已经实现。实际状态以仓库代码、测试和运行验证为准；方案变更与对应实现一并评审，不能以文档更新冒充功能完成。

## 维护规则

- 项目 PRD、架构决策、接口说明、部署文档、实施计划和项目复盘保留在所属仓库。
- 使用仓库相对链接；方案改名或移动时更新入口及引用。
- 现行方案直接更新，不并行维护不同版本正文；历史由 Git 追踪。
- PRD 统一需求编号和交付边界，技术方案定义实现边界，实施计划引用需求编号，不另建产品范围。
- Obsidian 可保留项目导航和跨项目通用学习，不存放重复项目方案。
- 不提交个人知识内容、凭据、运行数据库或完整知识库。
